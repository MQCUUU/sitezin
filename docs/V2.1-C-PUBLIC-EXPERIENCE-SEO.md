**Data:** 2026-09-28
**Escopo:** melhorar a experiência pública do MyCatalog (Home de
visitante, indexação, metadata, JSON-LD, robots/sitemap, favicon/PWA),
sem transformar o produto numa landing SaaS genérica e sem tocar a
experiência autenticada além do necessário para compartilhar
estrutura. V2.1-A e V2.1-B não foram reabertas.

## 2. Correção de herança de `robots`

Root layout continua `robots:{index:false, follow:true}` por padrão
(conservador — decisão mantida, não alterada). Cada página pública nova
ganhou seu próprio override explícito, no mesmo padrão já usado por
`/title/[type]/[id]` desde antes desta fase:

- `app/page.tsx` — convertido de Client Component puro para Server
  Component (só a casca de `metadata`) + `components/HomeClient.tsx`
  (toda a lógica existente, guest e autenticada, movida sem alteração
  de comportamento — só o nome do export mudou).
- `app/discover/layout.tsx` — novo, mesmo padrão do title/collection/u.

Não foi criada nenhuma abstração nova de "layout público genérico" —
o padrão de layout-irmão já estabelecido (title/collection/u) provou
ser simples e suficiente; replicá-lo é menos frágil do que introduzir
uma composição nova.

## 3. Hardening de `lib/site-url.ts`

**Antes:** `normalizeSiteUrl` aceitava `http://localhost`/`127.0.0.1`
sem checar o ambiente — o bug real (`og:url=http://localhost:3000` em
produção) foi corrigido manualmente na Vercel, mas nada no código
impedia a mesma reconfiguração incorreta de acontecer de novo.

**Depois:** nova função `isProductionRuntime()` (`process.env.VERCEL_ENV
=== "production"` — não `NODE_ENV`, que também é `"production"` em
builds locais e não distingue Preview de Production). Uma URL local só
é aceita quando `isProductionRuntime()` é falso; em produção real, cai
no fallback (`VERCEL_PROJECT_PRODUCTION_URL` válido, ou o hardcode
`https://catalogmy.vercel.app`).

**Teste "unitário equivalente"** (não existe Jest/Vitest no projeto —
só Playwright para e2e; não instalado nada novo por causa disso, `node
--experimental-strip-types` roda o `.ts` real diretamente, sem cópia da
lógica):

| Caso | Resultado |
|---|---|
| DEV + `NEXT_PUBLIC_SITE_URL=localhost` | permitido — **PASS** |
| PROD + `NEXT_PUBLIC_SITE_URL=localhost` | rejeitado, cai no fallback — **PASS** |
| PROD + URL https válida | aceita — **PASS** |
| PROD + `VERCEL_PROJECT_PRODUCTION_URL` válido, sem `NEXT_PUBLIC_SITE_URL` | aceita esse host — **PASS** |
| PROD + `VERCEL_PROJECT_PRODUCTION_URL` também local (hipotético) | fallback — **PASS** |
| PREVIEW + localhost | permitido (só `"production"` exato é bloqueado) — **PASS** |

6/6 PASS. Nenhum valor de env impresso durante o teste.

## 4. Perfis públicos (`/u/[username]`)

Auditado, **não alterado** — já estava correto desde uma fase
anterior: `robots` é condicional em runtime (`app/u/[username]/
layout.tsx`), consultando `profiles.visibility`/`is_public` a cada
request. Um perfil que vira privado depois de indexado naturalmente
para de ser servido como `index:true` na próxima vez que o Google
rastreia — sem exigir nenhuma ação manual. Não precisou de correção
nesta fase.

## 5. Listas públicas (`/lists/[id]`)

**Decisão desta fase: manter noindex, documentar como decisão
futura** — exatamente a orientação do enunciado para casos de dúvida.

Por quê não segui o mesmo padrão de `/u/[username]` agora:
- `app/lists/[id]/page.tsx` é `"use client"`, sem `layout.tsx` irmão —
  precisaria do mesmo trabalho de criar um layout condicional
  (replicável, mas é escopo novo não pedido explicitamente).
- Diferente de perfil (uma entidade estável por usuário), uma lista
  pode ser criada/apagada/tornada privada com mais frequência e menos
  fricção — o risco de conteúdo indexado ficar orfão (lista apagada,
  ainda no índice do Google por um tempo) é maior.
- `app/robots.ts` usa `"/lists$"` (só a página exata "/lists", não
  `/lists/[id]`) — **deliberado**, para não fechar a porta de indexar
  listas públicas individuais numa fase futura, caso essa decisão seja
  tomada. Bloquear via `robots.txt` teria sido mais difícil de reverter
  do que manter só a meta tag `noindex` herdada (que já é dinâmica por
  natureza).

**Recomendação para o futuro:** se decidirem indexar listas públicas,
replicar o padrão condicional de `/u/[username]/layout.tsx` (checar
`is_public` a cada request, nunca supor estático).

## 6. Collections (`/collection/[id]`)

Já estava `noindex` explícito e coerente com `robots.ts` desde antes
desta fase — confirmado deliberado (não acidental), documentado, sem
alteração.

## 7. JSON-LD (títulos)

Adicionado em `app/title/[type]/[id]/layout.tsx`, server-rendered
(`<script type="application/ld+json">` no próprio layout, não no client
component de 2.644 linhas). `schema.org Movie` para filme, `TVSeries`
para série.

**Dados usados** (só o que o TMDB realmente retorna, já buscado por
`detailsTMDB` — sem fetch extra, Next dedupe o `fetch()` idêntico
chamado por `generateMetadata` e pelo layout na mesma renderização):
`name`, `description` (overview), `image`, `datePublished`, `genre`,
`actor` (até 10 do `credits.cast`), `director` (filme,
`credits.crew` com `job==="Director"`) / `creator` (série,
`created_by`), `sameAs` (`https://www.themoviedb.org/{type}/{id}`,
sempre montável), `url` (canonical absoluto).

**`aggregateRating`** — só quando `vote_average > 0 && vote_count > 0`
(nunca um rating vazio/incompleto). Fonte é **sempre a nota pública do
TMDB** (`vote_average`/`vote_count`), documentado no próprio comentário
do código — a nota pessoal do usuário logado nunca chega a este
componente (o layout não tem acesso a sessão nem a `personal_rating`).

**Dados deliberadamente omitidos:** `reviewCount` (TMDB não expõe
contagem de reviews textuais nesse endpoint, só `vote_count` numérico
— usar `ratingCount`, não `reviewCount`, é a representação correta);
qualquer campo que exigiria fetch adicional (ex.: prêmios, bilheteria)
não é retornado por `detailsTMDB` hoje.

**Serialização segura:** `safeJsonLdString()` escapa `<` (→
`<`) para impedir que um `overview`/nome contendo literalmente
`</script>` feche a tag e injete HTML/JS arbitrário.

Validado em runtime: JSON-LD de filme (`/title/movie/155`) e série
(`/title/tv/1399`) parseiam como JSON válido, com `@type` correto.

## 8. Metadata — Home / Discover

**Home** (`app/page.tsx`, novo `metadata`): título
"MyCatalog — Filmes, séries e seu histórico em um só lugar", descrição
focada no que o produto faz, sem keyword stuffing, `robots:{index:true}`,
canonical `/`, OpenGraph/Twitter com a mesma cópia.

**Discover** (`app/discover/layout.tsx`, novo): título "Descobrir

(sem query string — filtros de gênero/ano/provider mudam o conteúdo
renderizado no client, mas nunca viram URLs indexáveis separadas,
evitando conteúdo duplicado/thin content). Validado: acessar
`/discover?genre=28` ainda resolve o canonical para `/discover`, sem o
query string.

## 9. Open Graph

Auditado Home, Discover, Title movie, Title TV — todos com `url`,
`title`, `description`, `type` coerente. Title já tinha imagem própria
(pôster/backdrop real do TMDB). Home e Discover **não tinham imagem OG
própria** — criada `app/opengraph-image.tsx` usando `next/og`
(`ImageResponse`, nativo do Next, nenhuma dependência nova instalada):
card de marca simples (ícone + "MyCatalog" + descrição curta, fundo
escuro, cor de acento), gerado sob demanda, servindo como fallback para
qualquer rota que não defina sua própria imagem OG. Não reutiliza
pôster de filme aleatório como imagem de marca (o enunciado pediu
explicitamente para evitar isso).

## 10. Favicon / identidade

Criado `app/icon.svg` (convenção de arquivo do Next — favicon

## 11. PWA manifest

`app/manifest.ts` ganhou `icons` (antes ausente): o mesmo `icon.svg`,
declarado duas vezes (`purpose: "any"` e `purpose: "maskable"`) —
navegadores modernos aceitam SVG em `icons` do manifest. Resto do
manifest (name/short_name/description/start_url/display/theme/
background/lang) já estava correto, não alterado. Sem service worker
novo (fora de escopo, instrução explícita).

## 12. `robots.ts` / `sitemap.ts`

**`robots.ts`:** `allow` ganhou `/discover` (agora indexável);
`disallow` ganhou `/insights` e `/lists$` (o `$` restringe ao path
exato "/lists" — "/lists/[id]" não é bloqueado, de propósito, ver §5).
Antes essas duas rotas ficavam de fora só por omissão — cobertas
apenas pela meta tag `noindex` herdada, agora também explícitas no
`robots.txt` por coerência com `proxy.ts`.

**`sitemap.ts`:** ganhou uma entrada para `/discover` (`changeFrequency:
daily`, sem `lastModified` — conteúdo dinâmico/filtrável, não uma
entidade com data própria). Limite de 5000 títulos e comportamento de
falha do banco (retorna só a home, não derruba o build) **não foram
alterados** — já eram razoáveis.

## 13. Auth pages

`/login`, `/signup` — layout preservado, não redesenhado. Metadata já

## 14. Performance da Home pública

- `/` agora é **estática** (`○`, prerendered) no build — antes também
  era Client Component mas sem a casca de Server Component; a mudança
  não piora nada, e potencialmente ajuda (o HTML da casca é gerado uma
  vez, não por request).
- A rail "Em alta agora" só busca dados (`fetch("/api/discover")`)
  **depois** de confirmar `authReady && !user` — zero chamada extra
  para usuário autenticado (que nunca renderiza esse branch).
- Reaproveita `/api/discover` já existente (sem filtro, 1 chamada, TMDB
  já teria sido chamado de qualquer forma por quem acessasse
  `/discover` normalmente) — nenhuma duplicação de implementação,
  nenhum N+1 novo.
- Limite de 10 itens na rail (dentro da faixa 6-12 pedida).
- Erro/vazio degradam graciosamente: a seção inteira some
  (`trendingGuestState !== "pronto" || length === 0`), sem quebrar o
  resto da Home.
