# V2.1-D — Performance & Escala

**Data:** 2026-09-29
**Escopo:** fazer Home autenticada, Para Você e Collection escalarem para
bibliotecas grandes sem mudar a experiência. Baseado em
[`docs/V2.1-POST-V2-AUDIT.md`](./V2.1-POST-V2-AUDIT.md) (HOME-02,
FORYOU-02, COLLECTION-01). V2.1-A/B/C não foram reabertas.

---

## 1. Baseline (TEST, fixture real)

Usuário descartável com **1000 `library_items`** (6 status, ~20% favoritos,
~25% com nota). Medido **antes** de qualquer mudança de código. Tempo é só
referência secundária (varia por ambiente); o critério é volume de dados.

| Superfície | Antes |
|---|---|
| Home | `GET /api/library` inteira: **1000 registros, ~776 KB**; o array inteiro era filtrado/ordenado 6x no browser e renderizado em cada prateleira |
| Para Você | client: `GET /api/library` inteira (**1000 registros, ~776 KB**); server: `SELECT` de **1000 registros** em memória a cada requisição (inclusive cada "carregar mais") + `user_hidden_titles` inteira. Resposta ~52 KB; ~19,4 s |
| Collection | `/api/collection/263` (~6 KB) **+ `GET /api/library` inteira (1000 registros, ~776 KB)** só para cruzar 3 filmes |

## 2. Arquitetura nova

### Home — `GET /api/home` (novo)
Auth obrigatório. Devolve **só** o que a Home usa:
- `totals`: 1 agregado SQL (`COUNT`/`AVG` com `FILTER`) — payload constante:
  `library`, `watching`, `want`, `watched`, `favorites`, `rated`,
  `average_rating`, `completion_base`.
- 4 prateleiras (`watching`, `want`, `best`, `recent`), cada uma com
  **`LIMIT 12`** e ordenação no banco, no mesmo formato de linha de
  `GET /api/library` (o client mantém o achatamento `...item.media`).
- `Server-Timing: db;dur=…, total;dur=…` (só durações, nenhum SQL/id).
- Calendário/Atividade **mantêm** seus endpoints próprios (contratos já
  enxutos, sem duplicar regra de negócio).
- Client: prateleiras e totais vêm prontos (nenhum filtro/sort sobre a
  biblioteca). **Cache de sessão versionado** `mycatalog:home:v2:` →
  `v3:` + validação `isHomeData()` — cache antigo/incompatível é ignorado,
  nunca quebra a tela.

### Para Você
- **Server** (`/api/for-you`): sem materializar a biblioteca.
  - seeds: `ORDER BY score DESC LIMIT MAX_SEEDS` no SQL (mesmo score de
    `libraryScore`, calculado no banco). **`MAX_SEEDS = 60`** = 4 seeds/página
    × 15 páginas de "carregar mais": o crescimento da biblioteca não
    aumenta mais o trabalho. Fallback (assistidos) com `LIMIT 20`, só
    executado se não houver seeds.
  - estado dos candidatos e itens ocultos: `preloadCandidateState()` —
    1 query batched **por prateleira** (`= ANY($3::bigint[])`, ≤100 ids)
    só dos ids que o TMDB acabou de retornar; `user_hidden_titles` nunca
    mais é lida inteira. Parametrizado (sem SQL dinâmico com valores).
  - cada card já vem com `in_library`, `status`, `favorite` e agora
    também `library_id` e `personal_rating` (só campos usados pela UI).
- **Client**: removido o fetch de `/api/library`; o estado local é semeado
  por `mergeLibraryFromShelves()` a partir dos cards recebidos.

### Collection
- **`POST /api/library/state` (novo, compartilhável e estreito):** exige
  sessão (guest → 401), sempre escopado ao `user_id` da sessão, **máx. 100**
  pares `(media_type, tmdb_id)` validados (400 caso contrário), **uma**
  consulta com `unnest`, devolve só `library_id/tmdb_id/media_type/status/
  favorite/personal_rating` e só dos títulos que existem na biblioteca.
- A página busca a coleção (pública, inalterada) e **depois** chama o state
  **uma vez** com os ids das partes. Falha/401 não derruba a coleção.
- **Privacidade/cache:** `/api/collection/[id]` continua 100% pública e
  sem dados pessoais (não foi tocada). O estado pessoal vive num endpoint
  autenticado separado, `Cache-Control: private, no-store` — nada
  user-specific entra em resposta pública/cacheável.

## 3. Comparativo real (mesma fixture, 1000 itens)

| Superfície | Métrica | Antes | Depois |
|---|---|---|---|
| **Home** | registros de library | 1000 | **48** (4×12, teto fixo) |
| | payload | ~776 KB | **~37 KB** |
| | requests de library | 1 (`/api/library`) | 1 (`/api/home`) |
| **Para Você** | registros de library (server) | 1000 + hidden inteiro | **≤60 seeds + só candidatos** |
| | registros de library (client) | 1000 (~776 KB) | **0** (0 requests) |
| | resposta | ~52 KB | ~54 KB (com `library_id`/`personal_rating`) |
| | tempo (ref. secundária) | ~19,4 s | ~4,0 s |
| **Collection** | registros de library | 1000 | **2** (só as partes salvas) |
| | payload de state | ~776 KB | **~300 B** |
| | requests | coleção + library | coleção + **1** state batched |

Complexidade: O(N biblioteca) → O(K interface), K limitado.

Verificado na UI real (Playwright, logado, 1000 itens): Home renderiza 48
cards com **0** `GET /api/library`, sem erros de console novos.

## 4. N+1

Nenhum. For You: 1 query batched por prateleira (não por card).
Collection: 1 request para N filmes. Home: 5 queries fixas em paralelo
(1 agregado + 4 prateleiras) — número constante, independente do tamanho.

## 5. Índices auditados (`EXPLAIN` em TEST, 1000 linhas)

Todas as queries novas usam índices **já existentes**, com `LIMIT`:
`library_items_user_added_idx` (recentes), `library_items_user_rating_idx`
(melhores, Incremental Sort só sobre o resultado já ordenado por nota),
`library_items_user_updated_idx` (em andamento/fila). **Migrations: 0.**

## 6. Observabilidade

- **Server-Timing** em `GET /api/home` (`db`, `total`) — leve, sem expor
  SQL, ids ou conexão.
- **Web Vitals:** não existe coleta hoje e não há destino real
  (armazenamento/dashboard) — **não** foi criado reporter que descartaria
  os dados. Registrado como observabilidade futura (junto de OBS-01/02).
- **Erros (`error.tsx`/`global-error.tsx`):** seguem `console.error`; sem
  serviço externo configurado, não foi implementado pseudo-monitoramento.

## 7. Performance budgets (regressão)

- **Home:** nenhuma chamada à biblioteca inteira; cada prateleira ≤ 12
  itens; payload de `/api/home` ≪ 100 KB para qualquer tamanho de
  biblioteca.
- **Para Você:** biblioteca nunca materializada; ≤ 60 seeds; estado dos
  candidatos por query batched (≤ 100 ids).
- **Collection:** estado pessoal só dos ids presentes (≤ 100 por chamada).
- Teste rápido de regressão: com a fixture de 1000 itens,
  `/api/home` < 120 KB e `GET /api/library` inteiro = 0 na Home/For You/
  Collection.

## 8. Deferidos / documentados

- `GET /api/library` (sem `paginated=true`) continua existindo e sendo
  usado por outras telas — **contrato não alterado**; outros consumidores
  de fetch integral (ex.: Discover/Search para estado dos cards, lists,
  ranking já migrado em H1) ficam documentados para fase futura.
- Web Vitals / error tracking externo: dependem de destino de dados.
- Sem Redis/cache distribuído/materialized views (não necessários).

## 9. Arquivos

**Novos:** `app/api/home/route.ts`, `app/api/library/state/route.ts`.
**Alterados:** `components/HomeClient.tsx`, `app/for-you/page.tsx`,

## 10. Testes (TEST, servidor isolado, usuários/fixtures removidos)

15 verificações PASS: Home sem os ~1000 itens (48 linhas), limites por
prateleira, totais agregados, ordenação/filtros; For You com recomendações,
estado dos cards e fallback para usuário sem histórico; Collection guest
pública, estado correto, 1 chamada batched, 401 para guest, limite de 100,
validação de entrada, e **estado de outro usuário nunca vaza**.

## 11. Gate final de regressão (2026-09-28)

37 verificações de runtime em TEST (2 usuários descartáveis), todas PASS:

- **Home:** `sessionStorage` v3 é apenas *stale-while-revalidate* — a Home
  monta, pinta o cache (≤5 min) e **sempre** refaz `GET /api/home`; um cache
  stale injetado é sobrescrito. add/remove/status/favorite/rating refletem
  na reentrada. Sem polling; nenhum evento novo necessário (a Home não
  muta a biblioteca).
- **Para Você / Collection (UI real):** add, status, favorite/unfavorite,
  remove, filtros Filmes/Séries/painel; `library_id` coerente e
  `personal_rating` preservado; mutações usam `POST/PATCH/DELETE
  /api/library` existentes.
- **Collection > 100 títulos:** o caller antes truncava silenciosamente em
  100 (`.slice(0, 100)`). Agora `chunkLibraryStateIds()`
  (`lib/library-state-batches.ts`) divide em lotes de 100: **ceil(N/100)**
  requests em paralelo. 205 ids → 3 requests (100/100/5), todos 200. O
  endpoint continua recusando >100 (400).
- **Privacidade:** dois usuários, mesmos `tmdb_id`, estados e `library_id`
  distintos; resposta `private, no-store`.
- **`GET /api/library`** (integral, paginado, filtros) intacto; **0**
  fetches integrais em Home, Para Você e Collection.
