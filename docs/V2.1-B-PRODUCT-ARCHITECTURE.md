## Insights

**Implementação escolhida:** combinação A+B do enunciado — `/insights`
como hub real (não placeholder) **e** uma subnav visual compartilhada
(`components/InsightsSubNav.tsx`) renderizada no topo das 4 páginas
(`/insights`, `/stats`, `/ranking`, `/retrospective`), para que quem
chegue direto via bookmark/deep link em qualquer uma das 3 páginas
antigas perceba imediatamente que está dentro da área "Insights".

- **Rota nova:** `/insights` (`app/insights/page.tsx`) — 3 cards de
  navegação (Estatísticas "Entenda seus hábitos", Ranking "Veja seus
  títulos mais bem avaliados", Retrospectiva "Revise seus anos no
  MyCatalog"). **Sem fetch de dados** — decisão deliberada para não
  duplicar as APIs de `/api/stats`/`/api/ranking`/`/api/activity` só
  para montar um resumo na landing (instrução explícita do enunciado:
  "não criar dashboard gigante").
- **URLs antigas:** `/stats`, `/ranking`, `/retrospective` **inalteradas**
  — mesmo componente de página, mesma lógica, só ganharam
  `<InsightsSubNav active="..." />` logo após `<Search />`.
- **Estado ativo:** o item "Insights" da sidebar fica marcado `active`
  em `/insights`, `/stats`, `/ranking` e `/retrospective` — implementado
  em `components/Nav.tsx` com uma checagem especial (`INSIGHTS_ROUTES`),
  já que o `isActive` genérico do restante do menu compara só 1 rota
  por item. Validado em runtime: nenhuma outra rota fica marcada ativa
  ao mesmo tempo (checado nos 3 casos).

## Curtidos

**Comportamento anterior:** `/favorites` era uma segunda implementação
de página (fetch próprio, sem paginação/outros filtros, sem
`viewMode`/`onAddToList`), renderizando o mesmo `<PosterGrid>` com os
mesmos dados que `/library?favorite=true` já entrega — confirmado por
leitura de código **antes** de remover (`app/api/library/route.ts`
já aplica `favorite=true` como `WHERE` real).

**Verificação de segurança do redirect:** `/favorites` permanece em
`PRIVATE_ROUTES` (`proxy.ts` — o middleware roda antes de qualquer
redirect de `next.config.ts`). Um guest é barrado e mandado para
`/login?next=/favorites` **antes** de qualquer redirect; um usuário
autenticado passa pelo middleware e só então cai no redirect real.
Confirmado: nenhuma funcionalidade exclusiva existia em `/favorites`
que justificasse mantê-la como página própria.

**Comportamento novo:** `/favorites` → `HTTP 307` (via
`next.config.ts` `redirects()`, `permanent: false`) → `/library?
favorite=true`. `app/favorites/page.tsx` foi **removida** (a rota não
existe mais como componente, só como regra de redirect). Validado em
runtime com sessão real: `GET /favorites` autenticado resolve em
`/library?favorite=true`, HTTP 200 final.

**Ícone:** já era `Heart` em todo lugar exceto no item de nav removido
(`Nav.tsx` usava `Eye` — removido junto com o item, então o problema
desaparece por completo, não precisou de correção isolada). A instância
de `/favorites` na Home (`app/page.tsx:1672`, `QuickLink`) já usa
`Heart` — nenhuma mudança necessária ali.

## Lists / Auth (`proxy.ts`)

**Achado do LISTS-01** (V2.1 audit): `/lists` (tela "Minhas listas") não
estava em `PRIVATE_ROUTES`, mas simplesmente adicionar a string quebraria
`/lists/[id]` (lista pública individual), porque `pathMatches` usa
correspondência de prefixo (`pathname.startsWith(route + "/")`) — que
bate em `/lists/abc` também.

**Correção:** novo array `PRIVATE_EXACT_ROUTES = ["/lists"]` em
`proxy.ts`, checado por **igualdade exata** (`pathname === route`),
separado do `PRIVATE_ROUTES` de prefixo. `/lists` (exato) agora exige
sessão; `/lists/[id]` continua público por design, sem nenhuma mudança
de comportamento.

**Achado adicional durante esta fase:** `components/SessionSync.tsx`
mantinha uma **segunda cópia independente** da lista `PRIVATE_ROUTES`
(guard client-side para sessão perdida em runtime), sem `/insights` e
com o mesmo risco de prefixo para `/lists`. Corrigida em paralelo, com
o mesmo padrão (`PRIVATE_EXACT_ROUTES`), para não deixar as duas fontes
de verdade divergirem — não fazia parte do pedido original desta fase,
mas era necessário para a nova arquitetura funcionar de forma
consistente entre o gate de servidor (`proxy.ts`) e o guard de client
(`SessionSync.tsx`).

Validado em runtime: guest em `/lists` → redirecionado para
`/login?next=/lists`; guest acessando uma lista pública criada de
verdade (`POST /api/lists` com `is_public: true`) → HTTP 200, sem
redirect.
