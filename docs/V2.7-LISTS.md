## 2. Arquitetura

**Identidade durável do item = `media_id`.** Uma lista guarda "este filme/série",
não "esta linha da minha Biblioteca". `library_item_id` vira opcional e informativo.

| | Antes | Depois |
|---|---|---|
| PK de `custom_list_items` | `(list_id, library_item_id)` | `(list_id, media_id)` |
| `media_id` | — | `NOT NULL`, FK → `media` |
| `library_item_id` | `NOT NULL`, FK `ON DELETE CASCADE` | nulo, FK `ON DELETE SET NULL` |
| `added_at` | — | `timestamptz NOT NULL DEFAULT now()` |
| `custom_lists.is_public` / `updated_at` | só no espelho `lists` | colunas próprias (backfill de `lists`) |
| Descrição `''` / `'null'` | gravada | `NULL` |

Índices: `custom_list_items_order_idx (list_id, position, added_at, media_id)`,
`custom_list_items_media_idx (media_id)`, e o único
`custom_list_items_list_library_key (list_id, library_item_id)` mantido só para o
`ON CONFLICT` do app antigo. Trigger `custom_list_items_fill_media` (BEFORE INSERT)
preenche `media_id` a partir de `library_item_id` — compatibilidade com o app antigo.

`public.lists` continua como espelho de compatibilidade, escrito na mesma transação
que `custom_lists`. `list_items` (legado, 0 linhas) não é usado.

### Ordem de deploy
1. Migration (aditiva/compatível): app antigo continua adicionando, lendo e removendo
   (validado em TEST e em PROD com conta descartável: trigger + `ON CONFLICT` antigo + leitura).
2. Deploy do app novo.

### Rollback de código
- O schema V2.7 **permanece**. **Não** desfazer a migration em emergência.
- Pode-se voltar temporariamente ao deploy anterior na Vercel.
- Itens antigos (com `library_item_id`) continuam compatíveis: o app antigo lê, adiciona e remove.
- Itens criados pela V2.7 ficam com `library_item_id = NULL` — **inclusive** títulos que estão
  na Biblioteca — e também itens cujo título saiu da Biblioteca (FK `SET NULL`). O app antigo
  lê com `JOIN library_items`, então esses itens ficam **invisíveis e inoperáveis** na UI antiga
  (uma lista criada na V2.7 pode aparecer vazia), mas **permanecem preservados** no banco.
- Se o app antigo tentar adicionar à lista uma mídia que a V2.7 já colocou ali, o banco recusa
  (`409`, PK `(list_id, media_id)`): nada é duplicado nem alterado.
- Mutações do app antigo na mesma lista não tocam os itens V2.7. Novos itens do app antigo
  entram com `position = count` (pode empatar após remoções; o desempate por `added_at, media_id`
  mantém a ordem determinística na V2.7).
- Ao restaurar a V2.7, todos os itens reaparecem intactos (mesmo `media_id` e posição).
- Não apagar nem "corrigir" esses itens com SQL durante o rollback.

Comprovado empiricamente no TEST (app antigo `d3ed978` × V2.7 no mesmo banco): 26/26.

## 3. Regras

- **Autoridade = sessão.** `user_id` nunca vem do cliente. O app conecta como owner
  (BYPASSRLS), então o isolamento é no servidor; RLS não foi alterado nesta versão.
- **Privacidade:** lista privada para não-dono → `404 "Lista não encontrada."`,
  idêntico a UUID inexistente. Qualquer mutação de não-dono → 404, nada muda.
- **Visitante de lista pública** vê nome, descrição, títulos e dono — **nunca** status,
  nota ou resenha da Biblioteca do dono (`library_status` = `NULL`, sem `members`).
- **Perfil público** mostra só listas públicas (o dono vê todas). Pública → privada
  some do perfil imediatamente (sem cache).
- **Ordem:** `position, added_at, media_id`. Inserção no fim (`max+1`); mover renumera
  0..n-1 dentro de transação com `SELECT … FOR UPDATE` na lista (serializa movimentos
  concorrentes); remover deixa lacunas sem quebrar o determinismo.
- **Duplicata:** `ON CONFLICT (list_id, media_id) DO NOTHING` → `200 {already:true}`.
  A mesma mídia pode estar em listas diferentes.
- **Independência:** adicionar/remover/reordenar não toca Biblioteca, Diário, histórico
  nem Insights. Remover da Biblioteca não tira o título da lista.
- **Capa:** primeiros 4 títulos **com pôster**, na ordem da lista. 0 → fallback,
  1/2/3/4+ → composições fixas. Sem upload, nada salvo. Pôster quebrado → bloco neutro.
  No detalhe, sem busca, a capa acompanha a reordenação otimista; com busca, usa a
  capa da lista inteira devolvida pela API (não muda com o filtro).
- **Descrição:** `null`/`""`/espaços/`"null"` → `NULL`; vazia não renderiza linha.
- **Limites:** nome 2–80, descrição 300, 24 listas/página, 60 itens/página.

## 4. Decisões e limitações

- Reordenação acessível por botões ↑↓ (teclado, toque, leitor de tela com `aria-live`);
  **sem drag-and-drop** nesta versão (opcional no escopo).
- Espelho `lists` mantido; removê-lo exige versão própria. **Dívida registrada:**
  - leitores: app antigo lê `is_public` dele (`/api/lists/items`, `/api/lists`); a V2.7 lê
    `custom_lists.is_public`;
  - escritores: POST/PATCH/DELETE de `/api/lists` (mesma transação que `custom_lists`);
  - risco de divergência: escrita direta por SQL ou por cliente fora dessas rotas;
  - aposentadoria futura: confirmar zero leitores → parar de escrever → remover a tabela
    numa versão própria, depois que o rollback para o app antigo deixar de ser necessário.
- A seção de listas do perfil continua sujeita a `lists_visibility` do perfil.
- Adicionar títulos busca o catálogo TMDB (`/api/search`); filmes e séries apenas.
- Foco nos diálogos de Listas: `useDialogFocus` (onClose estável + foco inicial por
  efeito) — o primitivo `Dialog` não foi alterado.
